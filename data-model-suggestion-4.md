# Data Model Suggestion 4: Graph Database (Neo4j) with PostgreSQL Financial Sidecar

> Project: Music Rights Management · Candidate #441 · Generated: 2026-05-25

---

## Overview

This model uses a **graph database (Neo4j)** as the primary store for the music rights domain -- the interconnected web of works, recordings, parties, splits, territories, contracts, and PRO registrations -- paired with a **PostgreSQL sidecar** for financial data (statement lines, royalty calculations, payment runs, and FX rates) where relational integrity and decimal precision are non-negotiable.

The music rights domain is fundamentally a graph problem. Consider the question: *"Who is entitled to what percentage of the royalties generated by this recording in Germany?"* Answering it requires traversing:

1. **Recording** -> linked to **Work(s)** (a recording may embody multiple works if it contains samples or interpolations)
2. **Work** -> owned by multiple **Parties** (writers, publishers) via **Share** relationships
3. Each **Share** has territory-specific overrides, potentially through a **Sub-Publisher** in Germany
4. The **Sub-Publisher** may have their own collection arrangement with **GEMA** (the German PRO)
5. The **Contract** governing the sub-publishing deal specifies admin fees, advance recoupment terms, and reversion clauses
6. The **Contract** was created under a parent **Co-Publishing Agreement** that sets the writer/publisher split

In a relational database, answering this question requires joining 6-8 tables with complex WHERE clauses on date ranges and territory codes. In a graph database, it is a single path traversal:

```cypher
MATCH path = (rec:Recording {isrc: 'USRC12345678'})
    -[:EMBODIES]->(w:Work)
    <-[:OWNS_SHARE {territory: 'DE'}]-(p:Party)
    -[:GOVERNED_BY]->(c:Contract)
    -[:SUB_PUBLISHED_BY]->(sp:Party {country: 'DE'})
    -[:COLLECTS_VIA]->(pro:PRO {name: 'GEMA'})
RETURN path
```

The README itself notes: *"A graph-like structure suits the many-to-many relationships between works, recordings, rights holders, and territories better than a flat relational schema."* This model takes that observation seriously and implements it as the primary architecture.

## Neo4j Constraints and Indexes

```cypher
// Uniqueness constraints
CREATE CONSTRAINT work_id_unique FOR (w:Work) REQUIRE w.id IS UNIQUE;
CREATE CONSTRAINT work_iswc_unique FOR (w:Work) REQUIRE w.iswc IS UNIQUE;
CREATE CONSTRAINT recording_id_unique FOR (r:Recording) REQUIRE r.id IS UNIQUE;

CREATE CONSTRAINT release_id_unique FOR (rel:Release) REQUIRE rel.id IS UNIQUE;
CREATE CONSTRAINT release_upc_unique FOR (rel:Release) REQUIRE rel.upc IS UNIQUE;
CREATE CONSTRAINT party_id_unique FOR (p:Party) REQUIRE p.id IS UNIQUE;
CREATE CONSTRAINT party_ipi_unique FOR (p:Party) REQUIRE p.ipi_name_number IS UNIQUE;
CREATE CONSTRAINT territory_code_unique FOR (t:Territory) REQUIRE t.code IS UNIQUE;
CREATE CONSTRAINT contract_id_unique FOR (c:Contract) REQUIRE c.id IS UNIQUE;
CREATE CONSTRAINT registration_id_unique FOR (r:ProRegistration) REQUIRE r.id IS UNIQUE;
CREATE CONSTRAINT share_version_id_unique FOR (sv:ShareVersion) REQUIRE sv.id IS UNIQUE;

// Property existence constraints
CREATE CONSTRAINT work_title_exists FOR (w:Work) REQUIRE w.title IS NOT NULL;
CREATE CONSTRAINT recording_title_exists FOR (r:Recording) REQUIRE r.title IS NOT NULL;
CREATE CONSTRAINT party_name_exists FOR (p:Party) REQUIRE p.legal_name IS NOT NULL;
CREATE CONSTRAINT territory_name_exists FOR (t:Territory) REQUIRE t.name IS NOT NULL;

// Full-text search indexes
CREATE FULLTEXT INDEX work_search FOR (w:Work) ON EACH [w.title, w.genre, w.iswc];
CREATE FULLTEXT INDEX recording_search FOR (r:Recording) ON EACH [r.title, r.isrc];
CREATE FULLTEXT INDEX party_search FOR (p:Party) ON EACH [p.legal_name, p.display_name, p.ipi_name_number];

// Range indexes for temporal queries
CREATE INDEX work_created_at FOR (w:Work) ON (w.created_at);
CREATE INDEX recording_release_date FOR (r:Recording) ON (r.release_date);
CREATE INDEX contract_effective_date FOR (c:Contract) ON (c.effective_date);
```

## PostgreSQL Financial Sidecar

Financial calculations, statement ingestion, and payment processing require strict decimal precision, ACID transactions, and efficient bulk aggregation -- strengths of PostgreSQL. The Neo4j graph provides the entity IDs referenced by the financial tables.

### Statement Ingestion

```sql
CREATE TABLE statement_sources (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_name     VARCHAR(100) NOT NULL UNIQUE,
    source_type     VARCHAR(30) NOT NULL,
    neo4j_party_id  UUID,                -- references Party node in Neo4j
    parser_config   JSONB NOT NULL,      -- column mapping configuration
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE statement_batches (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_id           UUID NOT NULL REFERENCES statement_sources(id),
    file_name           TEXT NOT NULL,
    file_hash           VARCHAR(64),
    statement_period    DATERANGE NOT NULL,
    original_currency   VARCHAR(3) NOT NULL,
    total_amount        NUMERIC(16,4),
    line_count          INTEGER,
    matched_count       INTEGER DEFAULT 0,
    status              VARCHAR(30) NOT NULL DEFAULT 'pending',
    processing_stats    JSONB DEFAULT '{}'::jsonb,
    anomaly_report      JSONB,
    ingested_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at        TIMESTAMPTZ
);

CREATE TABLE statement_lines (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    batch_id            UUID NOT NULL REFERENCES statement_batches(id),
    line_number         INTEGER NOT NULL,
    
    -- Reported identifiers
    reported_isrc       VARCHAR(20),
    reported_iswc       VARCHAR(20),
    reported_title      TEXT,
    reported_artist     TEXT,
    
    -- Matched Neo4j node IDs
    matched_recording_id UUID,  -- Neo4j Recording.id
    matched_work_id      UUID,  -- Neo4j Work.id
    match_confidence     NUMERIC(5,2),
    match_method         VARCHAR(30),
    
    -- Financial data
    territory_code      VARCHAR(4),
    use_type            VARCHAR(50) NOT NULL,
    units               BIGINT,
    unit_rate           NUMERIC(12,8),
    gross_amount        NUMERIC(14,4) NOT NULL,
    currency_code       VARCHAR(3) NOT NULL,
    usage_period_start  DATE,
    usage_period_end    DATE,
    
    -- Raw source data
    raw_data            JSONB,
    
    status              VARCHAR(20) NOT NULL DEFAULT 'unmatched',
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    
    CONSTRAINT uq_stmt_line UNIQUE (batch_id, line_number)
);

CREATE INDEX idx_sl_batch ON statement_lines (batch_id);
CREATE INDEX idx_sl_isrc ON statement_lines (reported_isrc);
CREATE INDEX idx_sl_recording ON statement_lines (matched_recording_id);
CREATE INDEX idx_sl_work ON statement_lines (matched_work_id);
CREATE INDEX idx_sl_territory ON statement_lines (territory_code);
CREATE INDEX idx_sl_use_type ON statement_lines (use_type);
```

## Key Graph Queries (Cypher)

### 1. Find all rights holders for a recording in a specific territory

```cypher
// Who gets paid when this recording generates revenue in Germany?
MATCH (r:Recording {isrc: 'USRC12345678'})-[:EMBODIES]->(w:Work)
MATCH (p:Party)-[share:OWNS_WORK_SHARE {is_current: true}]->(w)
```

## Synchronization Between Neo4j and PostgreSQL

The two databases must be kept in sync. The synchronization strategy depends on the data flow direction:

### Neo4j -> PostgreSQL (Catalog matching during statement ingestion)

When statement lines are being matched to catalog records, the ingestion service queries Neo4j for matching works/recordings by ISRC, ISWC, or title+artist, then stores the matched IDs in the PostgreSQL statement_lines table.

```python
# Pseudocode for catalog matching
async def match_statement_line(line: StatementLine) -> MatchResult:
    # Step 1: Try ISRC match in Neo4j
    if line.reported_isrc:
        result = await neo4j.execute("""
            MATCH (r:Recording {isrc: $isrc})-[:EMBODIES]->(w:Work)
            RETURN r.id AS recording_id, w.id AS work_id
        """, isrc=line.reported_isrc)
        if result:
            return MatchResult(
                recording_id=result['recording_id'],
                work_id=result['work_id'],
                method='isrc',
                confidence=100.0
            )
    
    # Step 2: Try ISWC match
    if line.reported_iswc:
        result = await neo4j.execute("""
            MATCH (w:Work {iswc: $iswc})
            RETURN w.id AS work_id
        """, iswc=line.reported_iswc)
        if result:
            return MatchResult(work_id=result['work_id'], method='iswc', confidence=100.0)
    
    # Step 3: Fuzzy title+artist match
    result = await neo4j.execute("""
        CALL db.index.fulltext.queryNodes('recording_search', $query) 
        YIELD node, score
        WHERE score > 0.8
        MATCH (node)-[:EMBODIES]->(w:Work)
        RETURN node.id AS recording_id, w.id AS work_id, score
        LIMIT 1
    """, query=f"{line.reported_title} {line.reported_artist}")
    if result:
        return MatchResult(
            recording_id=result['recording_id'],
            work_id=result['work_id'],
            method='title_artist',
            confidence=result['score'] * 100
        )
    
    return MatchResult(method='none', confidence=0)
```

### Neo4j -> PostgreSQL (Share lookup during royalty calculation)

The royalty calculation engine queries Neo4j for the active shares at the usage date, including territory overrides, then performs all financial calculations in PostgreSQL.

```python
async def get_shares_for_calculation(work_id: UUID, territory: str, usage_date: date):
    return await neo4j.execute("""
        MATCH (p:Party)-[share:OWNS_WORK_SHARE]->(w:Work {id: $work_id})
        WHERE share.effective_from <= date($usage_date)
          AND (share.effective_to IS NULL OR share.effective_to > date($usage_date))
        OPTIONAL MATCH (p)-[ts:HAS_TERRITORY_SHARE {is_current: true}]->(t:Territory {code: $territory})
        RETURN
            p.id AS party_id,
            share.role AS role,
            COALESCE(ts.performance_share, share.performance_share) AS perf_share,
            COALESCE(ts.mechanical_share, share.mechanical_share) AS mech_share,
            share.id AS share_id
    """, work_id=str(work_id), territory=territory, usage_date=str(usage_date))
```

### PostgreSQL -> Neo4j (Financial summaries for dashboard)

After royalty calculations are complete, aggregated financial data is pushed to Neo4j as properties on the Party and Work nodes for dashboard queries.

```python
async def sync_financial_summaries(period: str):
    # Aggregate in PostgreSQL
    summaries = await postgres.execute("""
        SELECT party_id, work_id, rights_type,
               SUM(royalty_amount) AS total_royalties,
               SUM(payable_amount) AS total_payable
        FROM royalty_calculations
        WHERE calculation_period @> $period::date
        GROUP BY party_id, work_id, rights_type
    """, period=period)
    
    # Write summaries to Neo4j
    for s in summaries:
        await neo4j.execute("""
            MATCH (p:Party {id: $party_id})
            SET p.last_period_royalties = $total_royalties,
                p.last_period_payable = $total_payable,
                p.financial_updated_at = datetime()
        """, **s)
```

## Pros and Cons

### Pros

1. **Natural domain modeling.** The music rights domain is a web of many-to-many relationships: works connected to recordings connected to parties connected to territories connected to contracts connected to PROs. A graph database models these relationships as first-class citizens rather than as junction tables with foreign keys. The Cypher query language makes complex traversals readable and performant.

2. **Relationship-centric queries are trivial.** Questions like "find all parties connected to this work through any path" or "trace the chain of sub-publishing agreements across territories" are single Cypher queries that would require recursive CTEs or multiple JOINs in SQL. This is critical for a domain where rights chains can be 4-5 levels deep.

3. **Schema flexibility for evolving relationships.** Adding a new type of relationship (e.g., "AI training data attribution" connecting an AI-generated work to its training sources) requires no schema migration -- just create new nodes and relationships. This is important for a domain where regulatory requirements and business models are actively evolving.

4. **Visual debugging.** Neo4j Browser provides visual graph exploration, allowing rights administrators to literally see the web of relationships around a work. This is invaluable for dispute resolution and audit discussions with rights holders who are not database experts.

5. **Territory traversal performance.** Finding the effective share for a party in a specific territory is a single relationship hop, regardless of how many territories exist. In a relational model, the same query requires a LEFT JOIN with fallback to default shares -- and performance degrades as territory count increases.

6. **Financial integrity preserved.** By keeping all monetary calculations, statement data, and payment records in PostgreSQL, the model avoids the precision and transaction safety limitations of graph databases for financial operations. The graph handles the "who" and "what percentage"; PostgreSQL handles the "how much."

### Cons

1. **Dual-database operational complexity.** Running and maintaining two databases (Neo4j and PostgreSQL) doubles the infrastructure burden: separate backup strategies, monitoring, failover, and upgrade procedures. The synchronization layer between them is an additional failure point that must be robust and monitored.

2. **Consistency between databases.** When a share is updated in Neo4j, the next royalty calculation in PostgreSQL must use the new share. If the synchronization has lag, calculations may use stale data. Implementing distributed transactions across Neo4j and PostgreSQL is complex and typically requires eventual consistency with compensating actions.

3. **Neo4j licensing and cost.** Neo4j Community Edition lacks features needed for production (clustering, role-based access control, online backup). Neo4j Enterprise Edition or AuraDB (cloud) carry significant licensing costs. This contradicts the project's goal of being affordable for mid-market independents.

4. **Team expertise requirement.** Most developers are far more familiar with SQL than Cypher. Hiring and training for Neo4j expertise is harder and more expensive. The learning curve for graph thinking (vs. relational thinking) is steep.

5. **Bulk operations are slower.** Loading millions of statement lines, running royalty calculations across thousands of works, and generating CWR files for batch submission are all bulk operations that relational databases handle more efficiently. Neo4j is optimized for traversal, not for batch aggregation.

6. **No native decimal precision.** Neo4j stores numbers as 64-bit IEEE 754 floating point. For share percentages stored as relationship properties (e.g., `performance_share: 25.00`), this introduces floating-point precision issues. Shares must be stored as integers (basis points: 2500 = 25.00%) or as strings with application-level parsing. This is why financial data must live in PostgreSQL.

7. **Limited ecosystem tooling.** BI tools, reporting frameworks, and ORMs are built for relational databases. Connecting Metabase, Grafana, or dbt to Neo4j requires workarounds or custom connectors. Most of the platform's reporting needs will be served from the PostgreSQL side.

8. **CWR generation complexity.** CWR is a flat, record-oriented format (NWR, SPU, SPT, SWR, SWT lines). Generating CWR from a graph requires collecting nodes and relationships into the correct flat format, which is less natural than generating it from relational tables that already mirror the CWR record structure.

## Migration and Scaling Considerations

### Initial Deployment

Start with Neo4j AuraDB Free (or Community Edition for self-hosted) during development and early adoption. The free tier supports up to 200K nodes and 400K relationships, which accommodates a catalog of several thousand works. Move to a paid tier when the catalog exceeds this threshold or when clustering/RBAC is needed.

PostgreSQL runs as a single instance for the financial sidecar. The data volume from the PostgreSQL side scales linearly with statement ingestion volume.

### Data Migration

Migrating existing catalog data into the graph:

1. **Parties first** -- Create Party nodes for all writers, publishers, labels, and PROs.
2. **Works and Recordings** -- Create Work and Recording nodes, link them with EMBODIES relationships.
3. **Shares** -- Create OWNS_WORK_SHARE and OWNS_RECORDING_SHARE relationships.
4. **Territories** -- Create Territory nodes and HAS_TERRITORY_SHARE relationships.
5. **Contracts** -- Create Contract nodes and all associated relationships.
6. **Statement history** -- Import into PostgreSQL tables (this data does not go into the graph).

Use Neo4j's `LOAD CSV` or the `neo4j-admin import` tool for bulk loading.

### Scaling Path

1. **Neo4j clustering** -- Neo4j Enterprise supports causal clustering with read replicas. Route traversal-heavy queries (catalog browsing, rights chain exploration) to read replicas; direct write operations (share updates, new registrations) to the primary.

2. **PostgreSQL partitioning** -- Partition statement_lines and royalty_calculations by period, same as in Suggestion 1.

3. **Caching layer** -- Cache frequently-accessed graph patterns (e.g., "active shares for work X") in Redis to reduce Neo4j query load during royalty calculation runs.

4. **Graph sharding** -- If the catalog grows to millions of works (major-label scale), consider sharding the graph by label or publisher using Neo4j Fabric (federated queries across multiple databases). This is rarely needed for mid-market platforms.

### Cost Considerations

Neo4j Enterprise licensing or AuraDB Professional pricing adds $1,000-5,000+/month depending on data volume and instance size. For a mid-market platform targeting independent labels and publishers, this is a significant cost that must be factored into pricing. Alternatives to reduce cost:

- **Memgraph** -- An open-source, Cypher-compatible graph database with a more permissive license.
- **Apache AGE** -- A PostgreSQL extension that adds graph query capabilities (openCypher) to PostgreSQL, eliminating the need for a separate graph database. This is an emerging option that trades graph performance for operational simplicity.
- **Amazon Neptune** -- A managed graph database service with pay-per-use pricing that avoids upfront licensing costs.

If cost is a critical concern, Apache AGE running inside the existing PostgreSQL instance provides 80% of the graph benefits with 0% additional infrastructure cost.
